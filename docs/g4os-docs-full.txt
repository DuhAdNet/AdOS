# Criar um workspace
Source: https://docsg4os.g4business.com/getting-started/create-workspace

Veja o passo a passo para criar um novo workspace no G4 OS e começar com o contexto certo.

## O que acontece ao criar um workspace

Criar um workspace no G4 OS não é só abrir uma pasta com um nome novo.

Esse processo define o contexto inicial que vai orientar as primeiras sessões, as conexões que fazem sentido para aquele ambiente e a forma como o trabalho começa dentro do produto.

Em outras palavras: um bom workspace nasce com contexto suficiente para a IA operar melhor desde o primeiro uso.

## Antes de começar

Antes de criar o novo workspace, vale ter clareza sobre quatro decisões simples:

* qual será o nome desse workspace
* para qual empresa, área ou frente ele existe
* quais objetivos você quer priorizar primeiro
* quais ferramentas realmente valem ser conectadas já no começo

Isso evita criar um workspace genérico demais e ajuda o G4 OS a começar com mais aderência ao que você precisa executar.

## Passo 1: abrir o seletor de workspace e clicar em `Add Workspace`

O primeiro passo é abrir o seletor de workspace que fica logo abaixo da lista de sessões.

Ao clicar no nome do workspace atual, o G4 OS abre a lista de workspaces disponíveis e mostra a opção `Add Workspace` no final do menu. É a partir dali que você inicia a criação de um novo ambiente.

<img alt="Menu de workspace com a opção Add Workspace" />

*Abra o seletor abaixo da lista de sessões e clique em `Add Workspace` para começar a criação de um novo workspace.*

Esse passo é importante porque ele deixa claro que o novo workspace nasce como um contexto separado, e não como só mais uma sessão dentro do mesmo ambiente.

## Passo 2: preencher os dados básicos

Na primeira etapa, você define as informações essenciais do workspace.

Normalmente entram aqui:

* nome do workspace
* seu nome
* idioma e região
* empresa
* localização local do workspace

<img alt="Criação do workspace e preenchimento dos dados iniciais" />

*Criação do workspace e definição dos dados básicos do ambiente.*

### O que isso define na prática

* como o workspace será identificado dentro do app
* qual idioma e região servem como base inicial
* onde esse workspace será criado localmente
* qual é o primeiro conjunto de contexto que o G4 OS já pode reaproveitar

## Passo 3: escolher perfil e objetivos

Depois dos dados básicos, o G4 OS pede duas decisões que ajudam a moldar a experiência inicial:

* o `perfil de trabalho` que mais se aproxima do seu uso
* os `objetivos principais` que você quer destravar primeiro

<img alt="Seleção de perfil de trabalho e objetivos principais" />

*Escolha do perfil e das prioridades que vão orientar o começo do workspace.*

### Perfis que podem aparecer

* `Manager`
* `IC`
* `Executive`
* `Researcher`
* `Freelancer`
* `Customizado`

### Objetivos que costumam aparecer

* automatizar rotina
* resolver problemas mais rápido
* organizar projetos e contexto
* preparar reuniões e follow-ups
* escrever melhor e mais rápido
* pesquisar e sintetizar informações

Essas escolhas não travam o workspace. Elas servem para o G4 OS começar com sugestões, linguagem e estrutura mais próximas da sua realidade.

## Passo 4: conectar as ferramentas iniciais

Na etapa seguinte, você pode conectar as ferramentas mais importantes logo no começo ou deixar isso para depois.

Nesse fluxo de criação, normalmente aparecem conexões como:

* Gmail
* Google Calendar
* Google Drive
* Outlook Email
* Outlook Calendar

## Passo 5: escolher como quer começar

Depois das conexões iniciais, o G4 OS pede uma decisão sobre o formato do começo:

* `Fazer entrevista guiada`
* `Explorar por conta própria`

<img alt="Conexão das ferramentas principais e escolha do modo de começo" />

*Conexões iniciais e decisão entre onboarding guiado ou entrada direta no workspace.*

### Quando escolher cada caminho

Escolha `Fazer entrevista guiada` quando você quer refinar melhor contexto, rotina e prioridades antes de começar a operar.

Escolha `Explorar por conta própria` quando você já sabe o que quer configurar e prefere entrar no app mais rápido.

## Passo 6: revisar a primeira sessão criada

Quando o workspace é finalizado, o G4 OS já abre a primeira sessão com um resumo do que foi definido durante a criação.

<img alt="Primeira sessão aberta com o resumo do setup inicial" />

*Primeira sessão do workspace com o contexto inicial preparado pelo onboarding.*

Esse resumo inicial costuma incluir:

* pessoa responsável
* idioma e região
* empresa
* perfil de trabalho
* objetivos escolhidos
* forma de começo selecionada
* fontes conectadas, quando houver

Esse é o melhor momento para validar se o contexto inicial ficou correto. Se algo estiver impreciso, vale ajustar antes de seguir para a primeira tarefa real.

## O que acontece depois da criação

Depois que o workspace nasce, ele passa a concentrar:

* sessões
* contexto acumulado
* conexões
* arquivos e referências
* automações e rotinas daquele ambiente

Por isso, a criação do workspace define muito mais do que um nome. Ela define a base operacional daquele contexto.

## Como criar um workspace melhor

Algumas escolhas simples melhoram bastante o resultado:

* use um nome claro e específico
* comece com poucos objetivos, não todos de uma vez
* conecte só as ferramentas que ajudam no primeiro fluxo que você quer validar
* revise a primeira sessão antes de abrir novas conversas
* trate cada workspace como um contexto operacional distinto

## Quando vale criar outro workspace

Geralmente faz sentido criar um novo workspace quando você quer separar:

* empresas diferentes
* times ou áreas com operação própria
* frentes de trabalho com contexto muito distinto
* ambientes que precisam de conexões, regras ou memória separadas

# Introdução
Source: https://docsg4os.g4business.com/index

Conheça o G4 OS, o AI Operational System da sua empresa.

## O que é o G4 OS?

O G4 OS é o `AI Operational System` da sua empresa.

Em vez de usar IA em conversas isoladas, o G4 OS coloca a IA dentro da operação real do time. Você conecta as ferramentas, os processos e o contexto que já existem, e passa a executar com mais continuidade, mais contexto e menos retrabalho.

Na prática, ele vira a camada onde trabalho, contexto e execução se encontram. É ali que seu time organiza sessões, conecta ferramentas, opera com agentes e automatiza rotinas sem precisar recomeçar do zero a cada nova conversa.

O objetivo não é só responder perguntas. O objetivo é ajudar sua empresa a `conectar tudo`, `gerenciar tudo` e `executar melhor` a partir de um único lugar.

## Não é só um chat com IA

O G4 OS foi pensado para times que já entenderam que IA sozinha não resolve o problema. O gargalo quase sempre está em outro lugar:

* contexto espalhado entre ferramentas
* decisões perdidas em conversas soltas
* tarefas recorrentes que continuam manuais
* dificuldade de transformar IA em operação consistente

Com o G4 OS, cada sessão pode virar uma frente de trabalho viva, com contexto acumulado, ferramentas conectadas e continuidade real entre o que foi decidido e o que precisa ser executado depois.

## Arquitetura local-first

O G4 OS foi desenhado para manter seus dados perto de você.

Credenciais, histórico de sessões e configuração de fontes ficam criptografados na sua máquina. Quando você conecta ERP, Gmail, Slack ou qualquer outra ferramenta, as chamadas saem diretamente do seu ambiente para o destino final — sem a G4 atuar como proxy intermediário.

# Agentes
Source: https://docsg4os.g4business.com/product/agents

Entenda como os agentes do G4 OS ajudam seu time a executar com mais autonomia e contexto.

## O que são agentes no G4 OS

Agentes são camadas operacionais de IA que trabalham com contexto, instruções, ferramentas e limites definidos.

Na prática, isso permite sair do uso genérico de chat e evoluir para uma operação em que a IA ajuda a analisar, organizar, decidir e executar com mais consistência.

## O que muda na prática

Em vez de depender apenas de prompts soltos, seu time passa a trabalhar com agentes que:

* entendem o contexto do workspace
* acessam fontes conectadas quando necessário
* seguem instruções e regras de uso
* podem apoiar fluxos recorrentes e automações

## Bons casos de uso

* preparação de reuniões
* consolidação de contexto e materiais
* acompanhamento de operações e pendências
* organização de informações dispersas
* execução assistida em fluxos internos

## O que diferencia um bom agente

Um bom agente não precisa parecer humano. Ele precisa ter função clara, acesso ao contexto certo e um escopo bem definido de atuação.

# Conexões
Source: https://docsg4os.g4business.com/product/connections/index

## Como pensar nas conexões no G4 OS

Conexões são o que trazem contexto, ferramentas e capacidade de execução para dentro do seu workspace.

Nem toda conexão funciona do mesmo jeito. Algumas são prontas e gerenciadas pelo produto, outras dependem de configuração técnica, e outras já entregam uma capacidade de agente pronta para uso.

## Comparação rápida

| Tipo                 | O que é                                         | Melhor quando                                                       | Onde abrir                             |
| -------------------- | ----------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------- |
| Conexões Gerenciadas | Integrações prontas do catálogo do G4 OS        | Você quer plugar apps conhecidos com menos configuração manual      | `Ferramentas > Conexões > Gerenciadas` |
| Agentes Gerenciados  | Agentes prontos com capacidades específicas     | Você quer execução especializada, multimodalidade ou geração        | `Ferramentas > Conexões > Agentes`     |
| MCPs                 | Servidores que expõem ferramentas via MCP       | Você precisa de ferramentas mais flexíveis, locais ou remotas       | `Ferramentas > Conexões > MCPs`        |
| APIs                 | Integrações diretas com endpoints e credenciais | Você já tem uma API definida e quer configurar o acesso diretamente | `Ferramentas > Conexões > APIs`        |

## Conexões Gerenciadas

Conexões gerenciadas são o caminho mais simples para plugar ferramentas populares no G4 OS.

Elas já vêm com a experiência do produto preparada para autenticação, reconexão, diagnóstico e uso em sessão. Na prática, isso reduz bastante a necessidade de configurar MCP, endpoint, escopo ou runtime manualmente.

  Veja o catálogo atual com cards por integração e um resumo do que é possível fazer em cada uma.

## Agentes Gerenciados

Agentes gerenciados são diferentes de uma conexão comum. Em vez de só conectar um sistema, eles já trazem uma capacidade operacional pronta, como entendimento multimodal, análise de documentos ou geração de imagens.

> **Beta:** agentes gerenciados são uma função beta e podem não estar disponíveis para todos os usuários, contas, workspaces ou builds do G4 OS.

<Card title="Explorar Agentes Gerenciados" icon="bot" href="/product/connections/managed-agents">
  Veja o catálogo atual de agentes, o que cada um faz melhor e onde eles aparecem no produto.
</Card>

## MCPs

MCPs são conexões baseadas em Model Context Protocol. Em vez de um catálogo pronto do G4 OS, você conecta um servidor que expõe ferramentas e capacidades para o produto consumir.

Esse é o caminho certo quando você precisa de algo mais customizado, quando a integração já existe em MCP ou quando faz sentido manter a lógica fora do G4 OS.

### Quando faz mais sentido

* quando sua integração já existe como servidor MCP
* quando você precisa expor ferramentas mais específicas do que uma API pronta
* quando a autenticação, o runtime ou a lógica da integração precisam ficar fora do produto

## APIs

APIs são conexões diretas com endpoints externos. Aqui o foco é configurar acesso a uma API específica, normalmente com URL, credenciais e parâmetros definidos por você.

É uma abordagem mais técnica e mais flexível do que as conexões gerenciadas, mas com menos abstração do produto.

### Quando faz mais sentido

* quando você já tem uma API interna ou externa bem definida
* quando não existe conector gerenciado para esse sistema
* quando você quer um controle mais direto sobre endpoint, auth e payload

## Como escolher sem complicar

* Comece por `Conexões Gerenciadas` quando o sistema já estiver no catálogo do G4 OS.
* Use `Agentes Gerenciados` quando o valor principal estiver na capacidade do agente, e não só no acesso à fonte.
* Use `MCPs` quando você precisar plugar ferramentas mais customizadas.
* Use `APIs` quando já existir uma integração técnica clara por endpoint.

# Privacidade e dados
Source: https://docsg4os.g4business.com/product/privacy-and-data

Entenda como os dados circulam no G4 OS, o que fica local e quando a infraestrutura da plataforma participa do fluxo.

## Resumo rápido

O G4 OS foi desenhado com uma arquitetura `local-first`.

No fluxo padrão, ele funciona como um orquestrador local: credenciais, histórico de sessões, configuração de fontes e chamadas para APIs externas ficam na sua máquina. Quando você conecta ERP, Gmail, Slack ou outras ferramentas via APIs próprias ou MCPs locais, a chamada sai da sua máquina para o destino final, sem a G4 atuar como proxy intermediário desse tráfego.

Isso não significa que nada nunca saia do seu ambiente. Significa que o fluxo principal do produto não depende de espelhar seus dados operacionais em servidores da G4 para funcionar.

## Como funciona na prática

### Visão geral: o que sai de onde

O diagrama abaixo mostra o fluxo completo — o que roda na máquina do usuário, o que vai para os LLMs externos, o que chega aos servidores da G4 e como as APIs de terceiros são acessadas pelo sistema.

```mermaid theme={null}
graph TD
    subgraph USER_MACHINE["Máquina do Usuário"]
        UI[Renderer UI\nReact + Jotai]
        IPC[IPC Bridge\nipc.ts / preload]
        MAIN[Main Process\nsessions.ts]
        SM[SessionManager]
        BACKEND[Agent Backend\nClaudeAgent / PiAgent / CodexAgent]
        INTERCEPT[Network Interceptor\npreload module]
        MCP[MCP Server Local\nstdio subprocess]
        CREDS[credentials.enc\nCriptografado local]
        LOCAL_DB[session.jsonl\nHistórico local]
    end

    subgraph EXTERNAL_LLM["LLMs Externos"]
        ANTHROPIC[api.anthropic.com]
        OPENAI[OpenAI / Compat]
        GEMINI[generativelanguage.google]
        BEDROCK[AWS Bedrock]
    end

    subgraph G4_SERVERS["Servidores G4 — g4oscloud.com"]
        TELEMETRY[api/telemetry/ingest\nMetadados hasheados]
        ENTITLEMENT[api/entitlements/me\nLicença do usuário]
        BUDGET[api/llm/budget/me\nCota de tokens gerenciados]
        UPDATE[api/updates/token\nAuto-update]

    subgraph EXTERNAL_APIS["APIs Externas — ERP, Gmail, Slack..."]
        ERP[API do ERP]
        GMAIL[Gmail API]

    UI -->|input do usuário| IPC
    IPC -->|IPC channel| MAIN
    MAIN --> SM
    SM --> BACKEND
    BACKEND -->|fetch global patchado| INTERCEPT
```

**Ponto central:** chamadas para ERP, Gmail, Slack e similares saem diretamente da máquina do usuário via MCP subprocess — sem passar pelos servidores da G4.

### Fluxo local padrão em texto

```text theme={null}
Interface do G4 OS
  -> execução local no seu computador
    -> provedor de IA escolhido por você
    -> APIs e sistemas externos conectados por você
```

### O que isso quer dizer

* o G4 OS roda e orquestra a operação localmente
* chamadas para APIs externas saem da máquina do usuário nos fluxos locais
* o conteúdo enviado ao modelo vai para o provedor de IA selecionado, não para a G4
* a G4 não precisa armazenar o histórico completo do seu workspace para a operação padrão funcionar

## O que normalmente fica local

No fluxo local padrão, estes itens permanecem no ambiente do usuário:

| Tipo de dado                   | Onde fica                         |
| ------------------------------ | --------------------------------- |
| Credenciais e tokens           | armazenamento local criptografado |
| Histórico de sessões           | arquivos locais do workspace      |
| Configuração de fontes         | arquivos locais do workspace      |
| Arquivos e contexto do projeto | diretórios e workspaces locais    |

### Como as credenciais circulam em tempo de execução

As credenciais nunca aparecem em logs, nunca ficam em disco durante a execução e nunca são incluídas na telemetria. O fluxo abaixo mostra o ciclo completo desde o armazenamento criptografado até o uso nas requisições.

```mermaid theme={null}
graph TD
    subgraph CRED_FLOW["Fluxo de Credenciais em Tempo de Execução"]
        STORED[credentials.enc\nAES criptografado em disco]
        MAIN_PROC[Main Process\ncarrega na memória]
        ENV_VARS[Env Vars do subprocess\nANTHROPIC_API_KEY etc]
        SDK_PROC[SDK subprocess\nherda env]
        HTTP_HDR[Header HTTP\nAuthorization: Bearer token]
        MCP_ENV[MCP Server subprocess\nenv vars]
        EXT_API[API Externa\nERP / Gmail / Slack]
    end

    STORED -->|decrypt na memória| MAIN_PROC
    MAIN_PROC -->|seta antes de spawn| ENV_VARS
    ENV_VARS -->|subprocess herda| SDK_PROC
    SDK_PROC -->|requisição HTTP| HTTP_HDR
    HTTP_HDR -->|TLS| LLM[API do LLM]

    MAIN_PROC -->|seta antes de spawn MCP| MCP_ENV
    MCP_ENV -->|subprocess herda| MCP_SRV[MCP Server]
    MCP_SRV -->|requisição HTTP com Bearer| EXT_API
```

## O que pode sair da sua máquina

Alguns dados precisam sair do seu ambiente para que o produto funcione:

* prompts e contexto enviados ao provedor de IA que você escolheu
* chamadas para APIs externas conectadas por você
* metadados técnicos limitados para autenticação, licenciamento, updates e telemetria operacional

## O que a G4 recebe no fluxo do produto

A plataforma pode receber dados técnicos necessários para operar o serviço, como:

* autenticação e entitlement da conta
* verificação de orçamento quando você usa recursos gerenciados
* checagem de updates
* telemetria técnica e estruturada do produto

No caso da telemetria, o produto usa identificadores hasheados para sessão e workspace em vez de IDs brutos, e o objetivo é medir uso técnico do sistema, não o conteúdo do que foi escrito.

### O que a telemetria envia — e o que ela nunca envia

```mermaid theme={null}
graph TD
    subgraph TELEMETRY_SENT["O que vai para g4oscloud.com/api/telemetry"]
        EV[Evento de Telemetria]
        EV --> F1[name: session_start / turn_completed / tool_used]
        EV --> F2[session_hash: SHA256 do sessionId]
        EV --> F3[workspace_hash: SHA256 do workspaceId]
        EV --> F4[provider_type: anthropic / openai / google]
        EV --> F5[model_id: claude-opus-4-6 etc]
        EV --> F6[app_version / platform / flavor]
        EV --> F7[turn_outcome: success / error]
        EV --> F8[error_family: auth / rate_limit / provider]
    end

    subgraph NOT_SENT["O que nunca é enviado"]
        NS1[Conteúdo das mensagens]
        NS2[Nomes de arquivos]

    end

    subgraph SENTRY_DETAIL["Sentry — Relatório de Erros"]
        SE[Stack trace de erro]

```

A telemetria é **comportamental e estruturada** — registra que uma sessão aconteceu, com qual modelo e com qual resultado. Nunca o conteúdo.

## Resumo: o que a G4 monitora de fato

| Canal           | O que vai                                                                         | O que não vai                                    |
| --------------- | --------------------------------------------------------------------------------- | ------------------------------------------------ |
| **Telemetria**  | Tipo de evento (hasheado), modelo usado, resultado (success/error), versão do app | Conteúdo de mensagens, dados do ERP, credenciais |
| **Sentry**      | Stack trace de erros, versão, plataforma                                          | Headers de auth (redactados), conteúdo de prompt |
| **Entitlement** | Email de login, licença ativa                                                     | Dados de sessão                                  |
| **Budget**      | Contagem de tokens consumidos                                                     | Conteúdo dos prompts                             |
| **Updates**     | Versão instalada                                                                  | Qualquer dado de sessão                          |

## O que a G4 não precisa receber no fluxo local padrão

No fluxo local padrão, a G4 não precisa receber:

* credenciais e chaves das suas integrações
* histórico completo das suas sessões para operar o app
* dados retornados por ERP, CRM ou APIs conectadas localmente
* caminhos locais e estrutura completa dos seus arquivos como base de operação da plataforma

## Quando essa arquitetura muda

Existem situações em que a infraestrutura da plataforma participa mais do fluxo. É importante deixar isso explícito.

### Conexões gerenciadas

`Conexões Gerenciadas` podem usar infraestrutura da plataforma para autenticação, catálogo, status e partes do runtime da integração.

Isso é diferente de uma API ou MCP puramente local. Se o objetivo for maximizar isolamento e previsibilidade do tráfego, prefira integrações locais ou MCPs que rodam no seu próprio ambiente.

### Recursos cloud opcionais

Recursos como `Cloud Sync`, colaboração e outras funções de nuvem mudam o fluxo porque, por definição, sincronizam parte dos dados com a infraestrutura da plataforma.

Esses recursos existem para backup, colaboração e continuidade, não porque o produto precise centralizar todo o seu contexto por padrão.

### Provedores e recursos gerenciados

Quando você usa provedores gerenciados, créditos da plataforma ou agentes gerenciados, parte do controle operacional passa pelos serviços da G4 para autenticação, orçamento, catálogo e roteamento técnico da funcionalidade.

Ainda assim, isso não transforma o G4 OS em um espelho permanente de todo o seu workspace.

## Como pensar segurança na prática

* use suas próprias chaves e integrações quando quiser o maior controle possível
* prefira APIs próprias e MCPs locais para sistemas sensíveis
* deixe recursos cloud opcionais desligados quando a política exigir operação mais local
* revise permissões, fontes e workspaces antes de ampliar automações

## Em uma frase

O G4 OS foi pensado para operar com contexto e execução perto do usuário, não para depender de copiar todo o contexto da empresa para a nuvem da G4.

# Segurança e controle
Source: https://docsg4os.g4business.com/product/security

Entenda como o G4 OS ajuda a operar IA com mais governança, limites e confiança.

## IA com governança operacional

Para gerar valor real no time, IA precisa de contexto e autonomia na medida certa, mas também precisa de controle.

O G4 OS foi desenhado para equilibrar velocidade com governança operacional.

## O que isso significa na prática

* controle sobre acessos e permissões
* regras sobre uso de ferramentas e fontes
* separação de contexto por workspace e sessão
* limites claros para fluxos recorrentes e automações

## Network Interceptor: transparência no tráfego com os LLMs

O G4 OS usa um `Network Interceptor` que roda como módulo de preload e intercepta as requisições antes de chegarem ao SDK do LLM. Ele não monitora o conteúdo das mensagens — existe para três funções específicas:

1. **Injetar metadados de UI nas tools** — para mostrar feedback como "Buscando email..." na interface durante execução de tools
2. **Otimizar o cache de prompts** — ajusta o TTL de `cache_control` para 1 hora, reduzindo custo e latência em sessões longas
3. **Capturar erros HTTP localmente** — salva erros 4xx/5xx em arquivo local temporário (`~/.g4os/api-error.json`, expira em 5 min) para diagnóstico

```mermaid theme={null}
graph LR
    subgraph INTERCEPTOR["Network Interceptor — roda como preload"]
        PATCH[globalThis.fetch\npatchado na inicialização]
        REQ_IN[Requisição saindo]
        RES_IN[Resposta chegando]

        subgraph REQUEST_MODS["Na Saída"]
            META_INJ[Injeta _intent e _displayName\nnos schemas de tools]
            CACHE_PATCH[Atualiza cache_control.ttl\nephemeral → 1h]
        end

        subgraph RESPONSE_MODS["Na Chegada"]
            META_STRIP[Remove _intent/_displayName\ndo SSE antes do SDK ver]
            ERR_CAPTURE[Captura erros 4xx/5xx\n→ ~/.g4os/api-error.json]
        end
    end

    PATCH --> REQ_IN
    REQ_IN --> META_INJ
    REQ_IN --> CACHE_PATCH
    META_INJ -->|headers + body| LLM_API[API do LLM]
    LLM_API --> RES_IN
    RES_IN --> META_STRIP
    RES_IN --> ERR_CAPTURE
    META_STRIP --> SDK[Claude Agent SDK]
    ERR_CAPTURE --> LOCAL_FILE[api-error.json\nexpira em 5 min]

    META_INJ -.->|salvo em disco| TOOL_META[tool-metadata.json\nlocal]
    META_STRIP -.->|lê do disco| TOOL_META
```

# Planos e Créditos
Source: https://docsg4os.g4business.com/support/billing-subscriptions

Entenda os planos disponíveis no G4 OS, como os créditos funcionam e como resgatar cupons.

## Como funciona

O G4 OS usa **créditos** como unidade de consumo. Cada interação com o assistente consome uma quantidade de créditos que varia de acordo com o modelo de IA utilizado. Modelos mais avançados consomem mais créditos por turno.

Todo workspace tem um **plano ativo** que define quantos créditos estão disponíveis por mês. Os créditos resetam automaticamente no primeiro dia de cada mês.

## Planos disponíveis

| Plano        | Créditos por mês | Para quem é                     |
| ------------ | ---------------- | ------------------------------- |
| **Gratuito** | 10 cr            | Para experimentar o G4 OS       |
| **Pro**      | 252 cr           | Para uso individual consistente |
| **Max**      | 566 cr           | Para uso individual intenso     |

> Os créditos do plano são o seu **saldo base mensal**. Créditos extras (via cupom ou concessão) são somados por cima e consumidos antes do saldo base.

### Planos corporativos

Empresas não têm um plano separado — o acesso corporativo é uma agregação de seats individuais. O administrador da empresa escolhe quantos seats de cada plano alocar e distribui entre os membros da equipe. Cada membro opera com o plano atribuído a ele, com seus próprios créditos mensais.

## Acompanhando seu consumo

Você encontra seu consumo atual em **Configurações > Uso**. A tela mostra:

* Créditos usados hoje vs. limite diário
* Créditos usados no mês vs. limite mensal
* Projeção de fechamento do mês
* Quais modelos consumiram mais créditos

Quando o saldo está próximo do limite, a barra de progresso muda de cor — azul quando acima de 80%, vermelha quando esgotado.

## Resgatar um cupom

<Frame>
  <img alt="Tela de Uso — seção Resgatar cupom com campo de código e botão Resgatar" />
</Frame>

Se você recebeu um código de cupom, pode resgatá-lo diretamente pelo app:

1. Vá em **Configurações > Uso**
2. No campo **Resgatar cupom**, cole o código recebido
3. Clique em **Resgatar**

Os créditos são adicionados ao seu saldo imediatamente. Créditos extras aparecem com um indicador separado na barra de uso mensal e são consumidos antes do seu saldo de plano.

## Quando os créditos acabam

Se você atingir o limite mensal, novas interações com o assistente ficam bloqueadas até o reset do mês. O histórico e as sessões existentes continuam acessíveis para leitura.

Em workspaces vinculados a uma empresa gerenciada, o administrador pode conceder créditos adicionais para desbloquear o acesso antes do reset. Veja [Uso → Quando os créditos acabam](/support/usage#quando-os-créditos-acabam).

# Cloud Sync
Source: https://docsg4os.g4business.com/support/cloud-sync

Sincronize um workspace entre dispositivos com token, push manual, prévia de pull e recuperação controlada.

## O que é Cloud Sync

Cloud Sync é o fluxo de continuidade e recuperação de um workspace entre dispositivos.

Ele foi feito para dois cenários principais:

* continuar o mesmo workspace em outra máquina
* recuperar um workspace a partir de um estado já enviado para a nuvem

Ele não substitui colaboração ao vivo. Para colaboração em sessão, o caminho certo continua sendo [Sessão colaborativa](/support/collaborative-session). Para continuar a mesma sessão no navegador ou no celular, use [Controle remoto](/support/remote-control).

## Como o processo funciona

Cloud Sync trabalha em cima de três ideias simples:

* um `token` conecta o mesmo workspace entre dispositivos
* `push` envia o estado local atual para a nuvem
* `pull` traz o estado remoto de volta, sempre com uma prévia antes da confirmação

## Fluxo recomendado entre dois dispositivos

### 1. No dispositivo de origem, gere o token e faça o primeiro envio

No dispositivo que já tem o workspace correto, o primeiro passo é abrir `Cloud Sync`, gerar o token e fazer o primeiro `Enviar para Nuvem`.

<img alt="Geração do token e primeiro envio para a nuvem" />

*Geração do token e início do primeiro push do workspace para a nuvem.*

O que importa aqui:

* o token aparece em claro só naquele momento
* você precisa copiar e guardar esse token imediatamente
* esse token é o que vai ligar o mesmo workspace ao outro dispositivo
* o primeiro `push` é o que cria a base remota que depois poderá ser restaurada

> O token não pode ser exibido novamente depois que essa etapa é dispensada.

### 2. No dispositivo de destino, importe o token

Na outra máquina, abra o workspace correspondente, vá até `Cloud Sync` e importe o token recebido.

<img alt="Importação do token em outro dispositivo" />

*Importação do token no dispositivo de destino para conectar o mesmo workspace.*

Depois da importação, a tela deixa de mostrar só `Conectar` e passa a exibir:

* `Status`
* `Ações`
* último `push`
* último `pull`

### 3. Antes de restaurar, revise a prévia do pull

No dispositivo de destino, o próximo passo costuma ser `Baixar da Nuvem`.

Antes de aplicar qualquer restauração, o G4 OS mostra uma `Prévia do Pull` com:

* máquina de origem do último push
* data e hora do push remoto
* arquivos novos
* arquivos modificados
* arquivos que serão excluídos localmente

<img alt="Prévia do pull antes da restauração" />

*Prévia do pull mostrando a origem do snapshot remoto e o impacto antes da confirmação.*

Esse é o momento de validar se você está trazendo o estado certo.

## O que a tela mostra quando já está conectada

<img alt="Status e ações do Cloud Sync depois da conexão" />

*Estado conectado com token mascarado, timestamps e ações manuais.*

Na prática, a tela passa a ter quatro blocos principais:

### Token

O token deixa de aparecer em claro e fica mascarado na área de `Status`.

### Último push

Mostra quando foi a última vez que esse workspace local enviou dados para a nuvem.

### Último pull

Mostra quando foi a última vez que esse workspace local restaurou dados da nuvem.

### Ações

* `Enviar para Nuvem`: envia o estado local atual
* `Baixar da Nuvem`: abre a prévia do pull antes da restauração
* `Desconectar`: remove o token desse workspace neste dispositivo

## O que entra no Cloud Sync

Cloud Sync prioriza contexto e configuração do workspace, não arquivos binários pesados.

Ele sincroniza principalmente:

* sessões
* configurações de fontes
* skills
* temas
* permissões
* arquivos textuais de configuração e histórico do workspace

## O que não entra no Cloud Sync

Alguns itens ficam explicitamente fora do sync:

* credenciais e tokens de autenticação
* anexos de sessão
* downloads
* respostas longas armazenadas fora do histórico textual
* chunks de gravação
* arquivos acima de `10 MB`
* conjuntos acima de `500 MB` no total

Em outras palavras: o foco é sincronizar estado operacional textual, não espelhar tudo o que existe no disco.

## O que precisa ficar claro antes de usar

* `push` e `pull` são manuais
* nada é sincronizado automaticamente em background
* o `pull` pode sobrescrever divergências locais e excluir arquivos locais ausentes no remoto
* por isso a `Prévia do Pull` existe e deve ser revisada antes da confirmação

## Casos comuns

* configurar o mesmo workspace em uma nova máquina
* fazer backup manual antes de trocar de dispositivo
* restaurar um workspace depois de recovery
* validar qual máquina fez o último push

## Quando usar Cloud Sync e quando não usar

Use `Cloud Sync` quando o objetivo for continuidade, backup ou restauração controlada do workspace.

Não use `Cloud Sync` como se fosse:

* colaboração em tempo real
* compartilhamento de sessão para outra pessoa
* controle remoto da mesma conversa

## Caminho no app

* `Configurações > Cloud Sync`

## Deep links úteis

* [Abrir Cloud Sync](g4os://settings/sync)
* [Abrir Workspace](g4os://settings/workspace)

## Resumo rápido

Cloud Sync conecta o mesmo workspace entre dispositivos com um token único, exige `push` e `pull` manuais, mostra uma prévia antes de restaurar, e sincroniza principalmente estado textual e configuração, sem incluir credenciais nem anexos pesados.

## O que é uma sessão colaborativa

Sessão colaborativa é o fluxo usado quando você quer que outro workspace do G4 OS entre na mesma conversa.

Ela é diferente de um link público. Em vez de só abrir uma página para leitura, o G4 OS cria um convite com duas partes:

* uma `URL de leitura`, que identifica a sessão compartilhada
* um `token de edição`, que autoriza a participação colaborativa

Quem recebe esse convite abre o G4 OS no próprio workspace, escolhe `Importar` e cola o texto completo. A partir daí, a sessão compartilhada passa a existir também naquele ambiente.

<img alt="Janela de sessão colaborativa no G4 OS" />

*Fluxo de criação e importação de convite colaborativo dentro do G4 OS.*

## Como funciona na prática

1. Você abre a sessão e entra em `Sessão colaborativa`.
2. O G4 OS gera a `URL de leitura` e o `token de edição`.
3. Você envia o texto completo do convite para a outra pessoa.
4. A outra pessoa abre o G4 OS, escolhe `Importar sessão colaborativa` e cola o convite.
5. O workspace de destino passa a acessar a mesma sessão compartilhada.

## O que cada parte do convite faz

### URL de leitura

A URL de leitura identifica a sessão compartilhada e serve como referência para o conteúdo que será aberto no outro workspace.

### Token de edição

O token de edição é o que libera a participação colaborativa. Sem ele, o convite fica incompleto.

Se o token não estiver mais disponível localmente ou já tiver expirado, o caminho correto é girar o token e gerar um novo convite.

## O que você pode gerenciar depois

Depois que o convite já existe, a própria tela de `Sessão colaborativa` permite controlar o acesso:

* `Copiar convite`: copia novamente o texto completo para convidar outra pessoa
* `Atualizar snapshot`: publica o estado mais recente da sessão compartilhada
* `Girar token`: invalida o token atual e força novos acessos a usarem um convite novo
* `Parar colaboração`: encerra o acesso colaborativo dessa sessão

> Girar o token desconecta quem já estava colaborando e exige reentrada com o novo token.

## Quando usar

* quando outra pessoa precisa continuar a conversa no próprio G4 OS
* quando o contexto precisa circular entre workspaces sem virar só um link de leitura
* quando você quer manter um canal controlado de colaboração sobre a mesma sessão

## Quando não usar

* se a outra pessoa só precisa ler a conversa, prefira [Compartilhamento](/support/sharing)
* se quem vai acessar é você mesmo em outro dispositivo, prefira [Controle remoto](/support/remote-control)

## Requisitos práticos

* a outra ponta precisa estar usando o G4 OS
* o convite deve ser enviado com `URL de leitura` e `token de edição`
* o import acontece dentro de um workspace ativo no app

## Caminho no app

* `Sessões > abrir uma sessão > menu de compartilhamento > Sessão colaborativa`

## Deep links úteis

* [Abrir Sessões](g4os://allSessions)

## Resumo rápido

Sessão colaborativa é o fluxo certo quando duas pontas do G4 OS precisam trabalhar sobre a mesma conversa, com convite controlado, importação dentro do app e revogação explícita quando necessário.


# Company Context
Source: https://docsg4os.g4business.com/support/company-context

Entenda como vincular seu workspace a uma empresa verificada e o que o badge de verificação representa.

## O que é o Company Context

O **Company Context** é o vínculo entre um workspace e uma empresa cadastrada no G4 OS.

Quando um workspace está conectado a uma empresa, os agentes passam a ter acesso a documentos, contexto organizacional e ferramentas compartilhadas daquela empresa — sem precisar repassar essas informações a cada nova sessão.

## Como vincular um workspace a uma empresa

1. Abra `Configurações > Workspace`
2. Localize a seção **Company Context**
3. Clique no seletor de empresa e escolha a empresa desejada
4. Confirme o vínculo

<img alt="Seletor de empresa no workspace com badge de verificação" />

*Seletor de Company Context no workspace. Empresas verificadas aparecem com o badge azul ao lado do nome.*

Depois de vincular, os agentes nas sessões desse workspace passam a usar o contexto daquela empresa automaticamente. Você pode desvincular a qualquer momento escolhendo **No company context**.

## O que é uma empresa verificada

Empresas verificadas exibem um **badge azul** ao lado do nome em:

* Lista de workspaces no workspace selector
* Sidebar da empresa
* Header de admin da empresa
* Viewer list

Esse badge indica que a empresa foi validada pelo G4 como a organização real correspondente àquele cadastro.

### Por que a verificação existe

A verificação resolve um problema prático: garantir que os colaboradores saibam que estão se conectando à **empresa real**, e não a um cadastro duplicado, desatualizado ou criado por engano.

Sem verificação, qualquer usuário com acesso ao admin poderia criar uma empresa com o mesmo nome. O badge azul é a confirmação de que o G4 validou aquela entidade.

## Critérios para verificação

Para que uma empresa seja elegível à verificação, ela deve atender a **todos** os seguintes critérios:

1. **Assinatura ativa** — a empresa precisa ter um plano pago vigente no G4 OS
2. **Mínimo de 10 usuários com seats pagantes ativos** — a conta deve ter ao menos 10 membros com licença paga ativa no momento da solicitação
3. **Solicitação formal ao G4** — o admin da empresa deve abrir uma solicitação oficial, acompanhada de documentação que comprove tratar-se da empresa real (contrato social, CNPJ, ou documento equivalente)

Após a análise e aprovação pelo G4, um admin do sistema marca a empresa como verificada no painel de administração.

## Relação com a gestão de usuários

A verificação está diretamente ligada à base de usuários da empresa:

* **Seats pagantes** são contados a partir dos membros com licença ativa em `Configurações da Empresa > Membros`
* Membros removidos ou inativos não contam para o critério de 10 seats
* Se a empresa perder usuários abaixo do mínimo ou encerrar a assinatura, a verificação pode ser revisada

Administradores podem acompanhar o status de membros e seats no painel da empresa.

## Quem pode solicitar verificação

Apenas **admins da empresa** no G4 OS podem iniciar o processo de verificação. O pedido deve ser feito diretamente ao suporte do G4 com a documentação necessária.

## O que muda após a verificação

* O badge azul aparece nos pontos descritos acima
* Colaboradores que veem o badge sabem que aquele cadastro foi validado
* O vínculo com um workspace verificado sinaliza para toda a equipe que o contexto compartilhado é o contexto oficial da empresa

## Caminho no app

* `Configurações > Workspace > Company Context`

# Contexto
Source: https://docsg4os.g4business.com/support/context

Gerencie documentos, estrutura, pessoas e PRs associados ao contexto compartilhado da empresa.

## O que é Contexto

`Contexto` é a área onde o workspace inspeciona e mantém contexto organizacional vinculado à empresa conectada.

Ela é diferente de uma sessão comum: o objetivo é guardar referências estruturadas que ajudam o agente a entender a operação, a organização e as decisões que devem ser reaproveitadas.

## Abas disponíveis

### Docs

Reúne documentos de contexto em markdown, com título, slug, nó responsável, regras de leitura e regras de edição.

Use para manter informações como:

* guias internos
* metas e prioridades
* políticas operacionais
* documentação de processos
* referências que o agente deve consultar com frequência

### Estrutura

Mostra a hierarquia de nós de contexto da empresa, como áreas, subáreas ou unidades operacionais.

Use para entender onde um documento, pessoa ou decisão pertence.

### Pessoas

Lista pessoas associadas ao contexto da empresa, quando esse módulo está disponível para o workspace.

Use para consultar responsabilidade, área, papel e relações operacionais importantes.

### PRs

Mostra propostas de alteração no contexto compartilhado, quando o fluxo de revisão está habilitado.

Use para revisar mudanças antes de promover conteúdo para o contexto oficial.

## Relação com Company Context

Para que a área de `Contexto` tenha dados, o workspace precisa estar vinculado a uma empresa em `Configurações > Workspace > Company Context`.

O vínculo define qual base organizacional será usada pelo agente e quais documentos, nós e pessoas aparecem nessa área.

Veja [Company Context](/support/company-context) para entender o vínculo e o badge de verificação.

## Caminho no app

* Menu lateral > `Contexto`

## Deep links úteis

* [Abrir Contexto](g4os://company-context)
* [Abrir configuração de Workspace](g4os://settings/workspace)

## Dica prática

Use `Contexto` para conhecimento que deve sobreviver a uma sessão específica. Use a sessão para trabalho em andamento, arquivos temporários e decisões que ainda precisam ser discutidas antes de virarem referência oficial.


# Dashboards
Source: https://docsg4os.g4business.com/support/dashboards

Use dashboards nativos para salvar painéis de workspace com fontes, layout, filtros e refresh reutilizáveis.

<Note>
  Dashboards estão em beta. A disponibilidade pode variar por build, workspace e conjunto de fontes conectadas.
</Note>

## O que são dashboards

Dashboards são painéis nativos salvos no workspace. Eles não são apenas respostas soltas em uma sessão: cada dashboard preserva uma definição durável com fontes, parâmetros, transformações, layout visual e histórico do último refresh.

Use dashboards quando uma análise precisa ser reaberta, atualizada ou acompanhada de forma recorrente.

<Frame>
  <img alt="Aba Dashboards no hub Ferramentas do G4 OS" />
</Frame>

## Como funcionam

Um dashboard normalmente reúne:

* **fontes conectadas** que fornecem os dados
* **parâmetros** como período, projeto, canal, status ou responsável
* **transformações** para filtrar, agrupar, ordenar ou calcular métricas
* **layout** em formato nativo, como KPIs, tabelas e gráficos
* **last run** com status, horário, linhas processadas e erros ou bloqueios

O objetivo é preservar o painel e atualizar os dados quando necessário, sem recriar o relatório do zero a cada sessão.

## O que o agente pode fazer

Quando as ferramentas de dashboard estão disponíveis, o agente pode:

* criar um dashboard novo a partir de um objetivo claro
* abrir um dashboard salvo na sessão
* atualizar os dados de um dashboard existente
* ajustar filtros, fontes, instruções ou layout quando você pedir uma edição

Atualizar um dashboard não deve redesenhar o painel. O refresh usa a definição salva, executa as fontes configuradas e substitui os dados materializados.

## Casos comuns

* acompanhar KPIs comerciais, financeiros ou operacionais
* transformar uma análise recorrente em painel reutilizável
* revisar um dashboard antes de uma reunião
* atualizar dados sem refazer a estrutura visual
* manter um relatório com fontes e filtros padronizados

## Caminho no app

* Menu lateral > `Ferramentas` > `Dashboards`

## Deep links úteis

* [Abrir Dashboards](g4os://dashboards)

O detalhe de um dashboard específico também pode ser aberto por deep link:

```text theme={null}
g4os://dashboards/dashboard/<slug-do-dashboard>
```

## Boas práticas

* defina o objetivo do painel antes de pedir a criação
* confirme quais fontes sustentam cada métrica
* use parâmetros para filtros que mudam com frequência
* prefira atualizar dashboards salvos em vez de pedir uma nova análise ad hoc
* revise permissões e credenciais das fontes quando o refresh falhar

Veja também [Ferramentas](/support/tools), [Conexões](/support/sources) e [Automação](/support/automation).


# Gerenciar Empresa
Source: https://docsg4os.g4business.com/support/empresa

Acompanhe consumo, gerencie usuários e configure políticas de crédito para toda a empresa no G4 OS.

## O que é Gerenciar Empresa

**Gerenciar Empresa** é o painel administrativo da empresa dentro do G4 OS. Ele oferece uma visão consolidada do consumo de créditos, dos membros ativos e das políticas de uso — tudo em um só lugar.

Apenas administradores da empresa têm acesso a esta área.

## Abas disponíveis

O painel é dividido em quatro abas:

* **Visão geral** — resumo de métricas de consumo, pacing e projeção do mês
* **Usuários** — listagem de membros com consumo individual e controles de override
* **Consumo** — gráfico diário de uso por toda a empresa
* **Políticas** — configuração de limites globais e grupos de política

## Visão geral

<Frame>
  <img alt="Painel Gerenciar Empresa — aba Visão Geral com métricas de consumo, usuários ativos e gráfico diário" />
</Frame>

A aba **Visão geral** exibe:

* **Modo de cobrança** — indica se a empresa opera no modelo ilimitado ou com pool de créditos definido
* **Mês selecionado** — selector de mês para navegar pelo histórico de consumo
* **Consumo do mês** — total de créditos consumidos no período selecionado
* **Usuários ativos** — número de membros com atividade no mês
* **Grupos de política** — quantidade de grupos de política específica configurados
* **Resumo do mês** — comparativo com o mês anterior e projeção de fechamento
* **Gráfico de consumo diário** — série temporal com consumo por dia; permite comparar mês atual e mês anterior

### Botão Atualizar

O botão **Atualizar** força um refresh dos dados. O cache tem 30 segundos de freshness e 10 minutos de stale — ou seja, dentro desse intervalo os dados são servidos do cache para evitar requisições duplicadas. Após o prazo, a próxima abertura do painel busca dados novos automaticamente.

## Usuários

A aba **Usuários** lista todos os membros associados explicitamente à empresa — não inclui usuários que apenas compartilham o mesmo domínio sem vínculo formal.

Colunas disponíveis:

| Coluna   | Descrição                                                |
| -------- | -------------------------------------------------------- |
| Usuário  | Email do membro                                          |
| Créditos | Consumo total no mês selecionado                         |
| Turns    | Número de interações com o assistente                    |
| Sessions | Número de sessões abertas                                |
| Limites  | Indica se há override de limites aplicado a esse usuário |

A tabela é **ordenável** por qualquer coluna. Clique no cabeçalho para alternar entre crescente e decrescente.

### Badge de auto-join

Membros que entraram automaticamente via domínio — ou seja, criaram um workspace com um e-mail cujo domínio está na lista de domínios permitidos da empresa — exibem o badge **auto-join**. Isso diferencia membros explícitos (convidados diretamente) de membros por matching de domínio.

> **Importante:** o consumo exibido na tabela considera apenas membros bound (vinculados) à empresa. Usuários com o mesmo domínio que **não** possuem vínculo formal não entram no cálculo.

## Políticas

<Frame>
  <img alt="Aba Políticas — configuração de limites globais, overflow de pool e domínios de auto-join" />
</Frame>

A aba **Políticas** controla as regras padrão aplicadas a todos os membros da empresa.

### Política global

A **Política global** define os limites padrão de crédito e as regras de associação automática por domínio. É aplicada a todos os usuários da empresa que não estejam em um grupo de política específico.

Campos disponíveis:

| Campo                     | Descrição                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Limite diário             | Máximo de créditos que um usuário pode consumir por dia                                                                  |
| Limite mensal             | Máximo de créditos que um usuário pode consumir no mês                                                                   |
| Overflow do pool          | Permite que usuários continuem usando o assistente após esgotar seu pool pessoal, usando o pool da empresa como fallback |
| Limite diário de overflow | Limite de créditos diários quando operando em overflow                                                                   |
| Limite mensal de overflow | Limite de créditos mensais quando operando em overflow                                                                   |
| Domínios permitidos       | Lista de domínios de e-mail que ativam a associação automática à empresa                                                 |
| Auto-join por domínio     | Quando ativo, usuários com e-mail de um domínio permitido são automaticamente vinculados à empresa ao criar um workspace |

### Grupos de política

Além da política global, é possível criar **grupos de política** para aplicar limites diferentes a subconjuntos de usuários — por exemplo, um time de produto com limite maior ou um grupo de teste com acesso restrito.

Cada grupo tem:

* Nome e descrição
* Lista de membros (e-mails)
* Configuração de limites própria (diário, mensal, overflow)

Membros em um grupo de política específico seguem as regras desse grupo, não as da política global.

## Ciclo de acesso de usuários

Administradores podem controlar o estado de acesso de membros individuais da empresa. O ciclo de acesso determina se um usuário pode ou não usar o G4 OS dentro do contexto gerenciado.

| Estado              | O que significa                                                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Ativo**           | Acesso normal; o usuário opera normalmente dentro das políticas configuradas                                                      |
| **Suspenso**        | Acesso temporariamente bloqueado, por exemplo por inadimplência ou revisão de conta; o usuário não consegue iniciar novas sessões |
| **Arquivado**       | Conta desativada e mantida no histórico; sem acesso operacional                                                                   |
| **Desprovisionado** | Remoção permanente do contexto gerenciado; os dados históricos são preservados                                                    |

Para alterar o estado de acesso de um usuário, acesse a aba **Usuários**, localize o membro e use o menu de ações. A mudança entra em vigor imediatamente.

> Suspender um usuário não remove seus dados nem o histórico de consumo. O estado pode ser revertido a qualquer momento enquanto a conta estiver suspensa ou arquivada.

## Planos e assinaturas

Administradores com acesso ao painel SaaS podem criar e gerenciar planos e assinaturas vinculadas à empresa. Planos definem as condições de consumo (créditos mensais, limites por usuário) e são atribuídos a usuários por meio de assinaturas.

Quando um plano é alterado, as permissões e limites dos usuários vinculados são sincronizados automaticamente em até 1 minuto. Não há necessidade de ação manual.

> Esta seção está disponível apenas em workspaces com o módulo SaaS habilitado. Se o painel não aparecer, entre em contato com o suporte.

## Limites mensais e enforcement em runtime

Os limites mensais configurados em **Políticas** são aplicados em tempo de execução — ou seja, o bloqueio acontece no momento em que o usuário tenta fazer uma nova chamada ao modelo, não de forma retroativa.

Quando um usuário atinge o limite:

* Novas chamadas ao modelo são bloqueadas imediatamente
* O usuário vê uma mensagem informando que o limite foi atingido
* O histórico de sessões e dados permanecem acessíveis (somente leitura)
* O contador reseta automaticamente no primeiro dia do mês seguinte

Administradores podem conceder créditos adicionais ou ajustar os limites a qualquer momento para desbloquear o usuário antes do reset mensal.

# Input
Source: https://docsg4os.g4business.com/support/input

Configure o comportamento do campo de texto no G4 OS — capitalização, correção ortográfica e tecla de envio.

## O que esta área cobre

# Controle remoto
Source: https://docsg4os.g4business.com/support/remote-control

Entenda como parear um navegador ou celular, liberar uma sessão e continuar o uso remoto do G4 OS.

## O que é controle remoto

Controle remoto é o fluxo usado quando você quer continuar a mesma sessão em outro dispositivo, como navegador desktop, navegador mobile ou celular.

Ele não publica a conversa para fora e não convida outro workspace para colaborar. O objetivo aqui é liberar a sua própria sessão para um dispositivo pareado.

<img alt="Janela de controle remoto no G4 OS" />

*Fluxo de pareamento, liberação da sessão e uso remoto no navegador ou celular.*

## Como funciona na prática

1. Você gera um `link de pareamento` no desktop.
2. Abre esse link no navegador ou celular que vai controlar o app.
3. Faz login com o mesmo e-mail usado no G4 OS.
4. Volta ao desktop, atualiza a lista de dispositivos e libera a sessão desejada.
5. Depois disso, o dispositivo pareado pode abrir o controle remoto e continuar dali.

## O que o pareamento faz

O pareamento transforma aquele navegador ou celular em um dispositivo conhecido pelo seu workspace.

Depois de pareado, o dispositivo pode aparecer na lista de autorização de sessões. Isso não significa que ele já tem acesso a tudo. Cada sessão ainda precisa ser liberada explicitamente.

## O que significa liberar a sessão

Liberar a sessão é o passo que autoriza um dispositivo pareado a acessar aquela conversa específica.

Na prática, o fluxo é separado em duas camadas:

* `parear o dispositivo`
* `liberar a sessão para esse dispositivo`

Essa separação evita que todo dispositivo pareado tenha acesso automático a todas as sessões.

## O que costuma ser lembrado

O mesmo navegador ou perfil costuma lembrar o pareamento e pode voltar ao controle remoto sem repetir tudo do zero.

Se você trocar de navegador, usar aba anônima, outro perfil ou uma webview diferente, é comum precisar gerar um novo link de pareamento.

## O que você consegue gerenciar

Na tela de `Controle remoto`, você pode:

* criar um novo link de pareamento
* atualizar a lista de dispositivos pareados
* liberar uma sessão para um dispositivo
* remover o acesso de uma sessão
* revogar um dispositivo quando ele não deve mais aparecer na lista

## Disponibilidade e energia

Para o controle remoto funcionar bem, o app desktop precisa continuar disponível.

O G4 OS tem a opção `Manter disponível para controle remoto`, que evita repouso automático enquanto houver dispositivo pareado e o computador estiver na tomada. Ainda assim:

* a tela pode desligar e o acesso continuar
* fechar a tampa do notebook desconecta o acesso remoto
* colocar o computador em repouso manualmente também desconecta

## Quando usar

* quando você quer continuar uma sessão no celular
* quando prefere operar a conversa pelo navegador sem perder o contexto do desktop
* quando o objetivo é mobilidade, e não colaboração entre workspaces

## Quando não usar

* se outra pessoa precisa entrar na sessão pelo próprio G4 OS, use [Sessão colaborativa](/support/collaborative-session)
* se você só quer enviar um link para leitura, use [Compartilhamento](/support/sharing)

## Caminho no app

* `Sessões > abrir uma sessão > menu da sessão > Controle remoto`

## Deep links úteis

* [Abrir Sessões](g4os://allSessions)

## Resumo rápido

Controle remoto é o fluxo certo quando a mesma pessoa quer continuar a sessão em outro dispositivo, com pareamento por link, login no mesmo e-mail e liberação explícita da conversa antes do acesso remoto.

## Veja também

* [Mensagens via Telegram](/support/telegram-messaging) — continue conversas pelo celular via Telegram sem abrir o app
* [Sessão colaborativa](/support/collaborative-session) — compartilhe uma sessão com outro usuário do G4 OS


# Modo reparo
Source: https://docsg4os.g4business.com/support/repair-mode

Entenda os diagnósticos de saúde, o reparo guiado e o log para suporte do G4 OS.

<Warning>
  **Beta:** Modo reparo é uma funcionalidade beta e ainda não foi disponibilizada para todos os usuários. Se não aparecer no menu de configurações, aguarde atualizações futuras.
</Warning>

## O que é o Modo reparo

`Modo reparo` é a área de diagnóstico e recuperação assistida do G4 OS.

Ela existe para ajudar quando o app continua abrindo, mas alguma parte do estado local ficou inconsistente depois de uma atualização, reinstalação, troca de versão ou migração entre máquinas.

<img alt="Tela de Modo reparo no G4 OS" />

*Tela de diagnósticos de saúde, reparo guiado e geração de log para suporte.*

## Quando usar

Use essa tela principalmente quando:

* sessões antigas pararam de abrir como antes
* o workspace atual ficou com caminhos quebrados
* a conexão gerenciada correta deixou de ser reconhecida
* você precisa validar a saúde local do app antes de chamar o suporte
* o time de suporte pediu um log técnico sem segredos

## O que esta tela faz

O `Modo reparo` combina três frentes:

* `diagnósticos somente leitura` para mapear o estado atual do app
* `reparo guiado` para corrigir metadados de sessão e revalidar o provedor gerenciado
* `log para suporte` para exportar um JSON técnico seguro de compartilhar

O ponto mais importante: a tela foi desenhada para ser conservadora.

Os diagnósticos e as prévias não alteram dados. Quando existe ação de aplicação, ela fica restrita a metadados de sessão ou à cópia de sessões importadas para o workspace ativo.

## O que o reparo guiado corrige

Na área `Reparo guiado`, a ação principal é `Corrigir sessões e provedor`.

Na prática, ela faz duas coisas:

1. Revalida a conexão gerenciada usada pelo app.
2. Revisa os `workspaces saudáveis` e normaliza somente metadados de sessão que costumam quebrar após mudanças de ambiente.

Os campos que podem ser ajustados nessa correção incluem:

* conexão gerenciada
* raiz do workspace
* diretório de trabalho
* `sdkCwd`
* runtime
* provedor
* modelo
* nível de pensamento

O que essa correção preserva:

* mensagens
* arquivos
* credenciais
* conteúdo das sessões

Se você quiser revisar o impacto antes de aplicar, use `Ver detalhes antes`.

## Como ler o resumo de saúde

O bloco `Resumo de saúde` mostra cartões por subsistema. Eles ajudam a identificar rapidamente onde está o problema:

* `Config e backup`: valida se a configuração principal e o backup estão legíveis
* `Workspaces`: mostra quantos workspaces estão saudáveis e quantos precisam de atenção
* `Sessões e índices`: verifica diretórios, arquivos de sessão e índices usados pelo app
* `Saúde do runtime`: indica se o runtime de execução das sessões está saudável
* `Artefatos de runtime`: checa se os artefatos empacotados exigidos estão presentes
* `Instalação da plataforma`: mostra diagnósticos específicos de macOS, Windows ou Linux
* `Credenciais e fontes`: revisa o armazenamento criptografado e diagnósticos salvos das fontes
* `Base de operações`: mostra se progresso, cancelamento e log técnico estão prontos para uso

Quando o topo da tela mostra `Status geral: Atenção` ou `Falha`, esses cartões ajudam a localizar a origem do problema antes de aplicar qualquer correção.

## Log para suporte

`Log para suporte` gera um arquivo JSON técnico com contexto suficiente para investigação, sem expor segredos.

Esse log inclui principalmente:

* dados do app, versão e distribuição
* resumo da configuração carregada
* resumo dos workspaces conhecidos
* snapshot completo dos diagnósticos
* últimas entradas do log interno do próprio modo reparo

Por padrão, o arquivo é salvo em `Downloads/G4 OS Support Logs`. Se preferir, você pode usar `Escolher local...` para salvar em outro lugar.

Depois da geração, o caminho do arquivo é copiado automaticamente, o que acelera o envio ao suporte.

## O que o Modo reparo não faz

É importante não esperar desta tela coisas que ela não promete fazer:

* ela não apaga nem reescreve o conteúdo textual das conversas
* ela não substitui binários empacotados do app
* ela não serve como reinstalação automática
* ela não executa verificações de assinatura e notarização como parte dos diagnósticos

Em outras palavras: o foco aqui é `diagnosticar`, `corrigir metadados` e `gerar contexto técnico`, não reinstalar o produto.

## Casos em que costuma ajudar

* depois de atualizar o G4 OS e perceber que sessões antigas ficaram inconsistentes
* depois de reinstalar o app em cima de uma instalação anterior
* quando o app abre, mas caminhos locais ou provedor parecem desalinhados
* quando você quer gerar um pacote técnico limpo antes de abrir um chamado

## Caminho no app

* `Configurações > Suporte` → tópico **Modo reparo** (quando disponível na sua conta)

## Deep links úteis

* [Abrir Support](g4os://settings/support)
* [Abrir Workspace](g4os://settings/workspace)
* [Abrir Cloud Sync](g4os://settings/sync)

## Resumo rápido

`Modo reparo` é a área certa para diagnosticar problemas locais do G4 OS, corrigir metadados de sessão sem mexer no conteúdo das conversas e gerar um log técnico seguro para suporte.


# Brain
Source: https://docsg4os.g4business.com/support/shared-brain

Use o Shared Brain para manter memória e contexto de workspace entre máquinas, com sync criptografado e gestão de nós confiáveis.

<Note>
  O Brain está em beta. Use para memória e contexto durável; não use para credenciais, tokens, anexos ou logs brutos de sessão.
</Note>

## O que é o Brain

O Brain é a camada de memória compartilhada do G4 OS.

Ele permite que um workspace mantenha contexto durável para o agente e, quando o sync criptografado está ativo, compartilhe esse contexto com outros workspaces ou computadores confiáveis que entraram no mesmo Shared Brain.

<Frame>
  <img alt="Visão geral do Shared Brain com abas de visão geral, memória e sync e nós" />
</Frame>

Na prática, ele serve para:

* lembrar decisões, preferências, convenções e correções importantes
* manter preferências de fontes e contas no escopo certo do workspace
* pesquisar memórias por lista ou grafo de contexto
* sincronizar memória entre máquinas sem sincronizar credenciais
* gerenciar quais computadores e workspaces participam daquele brain

## Quando usar

Use o Brain quando você quer que o agente tenha continuidade entre workspaces ou computadores.

Bons exemplos:

* "neste workspace, use Gmail X para e-mails comerciais"
* "a decisão atual do projeto é seguir o fluxo Y"
* "essa análise usa sempre o dashboard Z como referência"
* "esse erro já aconteceu; a correção correta foi esta"
* "este workspace compartilha contexto com outro computador meu"

Não use o Brain como substituto para Cloud Sync. Cloud Sync continua sendo o fluxo de backup/restauração do workspace inteiro. O Brain sincroniza memória canônica e sinais de nós; ele não espelha sessões completas, anexos ou tudo que existe em disco.

## Escopo: workspace, global e fontes

O Brain separa melhor o que deve ser memória do workspace e o que pode ser preferência global.

Na dúvida, trate como memória do workspace:

* preferência de fonte ou conta, como Gmail, Slack, MCP, ERP ou banco específico
* convenção de projeto
* decisão operacional daquele contexto
* raiz lógica, dashboard, fonte ou rotina válida só naquele workspace

Use memória global apenas quando a preferência é claramente da pessoa e faz sentido em todos os workspaces.

Exemplo: se em um workspace você usa um Gmail e em outro usa outro MCP ou outra conta Gmail, isso deve ficar ligado ao workspace correto, não como preferência global.

## Como ativar

Abra `Brain` no menu principal ou vá em `Configurações > Workspace` para ativar o recurso no workspace atual.

Ao iniciar, o app mostra duas opções:

### Criar brain daqui

Use quando este workspace é a origem do contexto.

O G4 OS ativa a memória local e abre uma sessão em modo execute para o assistente:

* ler contexto local do workspace
* revisar arquivos de contexto e memória já existentes
* criar ou atualizar artefatos necessários
* salvar memórias duráveis quando fizer sentido
* deixar orientação para futuras sessões usarem o Brain sem incomodar

### Importar shared brain

Use quando outro computador ou workspace já tem o Shared Brain.

Cole o código de configuração exportado do outro ambiente. Depois que o código é aceito, o G4 OS abre uma sessão em modo execute para o assistente:

* puxar primeiro o estado remoto do Brain
* pesquisar memórias e vizinhanças do grafo
* reconciliar memórias importadas com o contexto local
* propor instruções portáveis para futuras sessões usarem o Brain corretamente
* atualizar memórias, links e status quando houver confirmação
* manter o Brain atualizado daqui para frente sem editar arquivos locais em silêncio

O código de configuração contém o token de sync e a chave de criptografia. Use apenas em computador ou workspace confiável.

## Como o sync funciona

Quando o sync criptografado está pronto:

* o G4 OS roda sync em segundo plano periodicamente
* alterações locais feitas pelo agente disparam sync assíncrono logo depois
* outro computador pode receber um sinal criptografado para puxar novidades
* o app mostra último sync, saída pendente, nós confiáveis e eventos de auditoria

O sync não deve congelar a interface. Se um endpoint remoto falhar, a tela mostra o estado bloqueado/falhou e registra o motivo na auditoria.

## Vários computadores e vários workspaces

O modelo não assume que um usuário tem só uma máquina ou só um workspace.

Pense em:

```text theme={null}
Pessoa
  -> Computador A
     -> Workspace 1
     -> Workspace 2
  -> Computador B
     -> Workspace 3
```

Cada computador tem uma identidade de nó. Cada workspace pode ou não estar vinculado ao Shared Brain.

Um nó confiável não conecta automaticamente todos os workspaces daquele computador. A tela de sync mostra as participações de workspace para você ver e controlar quais vínculos estão ativos.

## O que é sincronizado

O Brain sincroniza memória canônica e metadados necessários para colaboração segura:

* registros de memória
* status da memória, como confirmada, rejeitada, supersedida ou expirada
* links entre memórias e nós do grafo
* conflitos e provenance quando aplicável
* estado de sync, nós confiáveis, vínculos de workspace e auditoria local

## Gestão de sync e nós

A aba `Sync e nós` mostra a identidade deste computador, os nós confiáveis, as participações de workspace e os eventos de auditoria.

Use essa aba para:

* exportar um código de configuração para outro workspace confiável
* importar um código recebido de outro computador ou workspace
* sincronizar manualmente quando quiser conferir o estado agora
* ver se o último sync enviou, baixou, aplicou ou ignorou alterações
* revisar quais nós e workspaces participam deste Brain
* revogar ou desvincular acessos quando um computador ou workspace não deve mais participar

Revogar um nó bloqueia syncs futuros daquele participante. Isso não apaga dados que já foram descriptografados localmente naquele computador.

Se a auditoria mostrar `falhou`, `bloqueado`, `negado` ou um código remoto, trate como sinal operacional: o sync pode estar incompleto até o endpoint, token, permissão ou presença remota ser corrigido.

## O que nunca deve entrar

Não salve nem sincronize:

* credenciais
* tokens OAuth
* chaves de API
* material de autenticação de fontes
* anexos
* logs brutos de sessão
* respostas longas completas
* dados temporários de uma tarefa que não precisam ser lembrados

Se uma informação parece segredo, ela deve ficar fora do Brain.

## Memórias e grafo

A aba `Memória` permite ver registros em lista ou grafo.

Use a lista para revisar, filtrar por tipo e arquivar memórias. Use o grafo para entender relações entre:

* preferências
* decisões
* observações
* resumos
* referências
* sessões ou contextos relacionados

Ao clicar em um nó, a tela mostra o conteúdo, fontes, status, sensibilidade, links e ações possíveis.

O agente também deve pesquisar de forma progressiva:

1. começar por status e busca ampla
2. olhar memórias diretas e recentes
3. expandir nós de contexto promissores
4. seguir links relacionados
5. só então criar, atualizar ou conectar uma memória

Isso evita concluir que "não existe memória" depois de uma busca estreita demais.

## Como o agente deve se comportar

Quando o Brain está ativo, o agente deve ser proativo, mas não inconveniente.

O comportamento esperado:

* lembrar memórias relevantes de forma discreta
* sugerir atualização quando perceber uma decisão, preferência ou correção durável
* perguntar uma vez antes de salvar, salvo quando você pediu explicitamente para lembrar
* atualizar status em vez de duplicar memória quando algo foi rejeitado, expirou ou foi supersedido
* conectar memórias relacionadas quando isso ajuda a busca futura
* manter preferências de fontes e contas no workspace correto
* propor alterações em `CLAUDE.md`, `AGENTS.md` ou arquivos de contexto e aguardar confirmação explícita antes de editar
* nunca gravar caminhos absolutos locais, usuário da máquina ou raiz local do app em memória durável ou instruções compartilhadas

Use caminhos relativos, IDs lógicos de raiz, nomes de workspace, source slugs e metadados de mapeamento de raiz. Caminhos absolutos podem aparecer como diagnóstico local, mas não devem virar regra durável do Brain.

## Onde encontrar

* Menu principal: `Brain`
* Configuração por workspace: `Configurações > Workspace`
* Aba de memória: `Brain > Memória`
* Aba de sync e nós: `Brain > Sync e nós`
* Deep link geral: [Abrir Brain no G4 OS](g4os://shared-brain)
* Deep link de configuração: [Abrir Workspace no G4 OS](g4os://settings/workspace)


# Compartilhamento
Source: https://docsg4os.g4business.com/support/sharing

Publique sessões, compartilhe links e entenda quando usar sessão colaborativa ou controle remoto no G4 OS.

## Quando usar cada opção

| Fluxo                    | Melhor quando                                                              | Quem acessa                     |
| ------------------------ | -------------------------------------------------------------------------- | ------------------------------- |
| Compartilhamento público | você quer mandar uma conversa para leitura ou revisão                      | qualquer pessoa com o link      |
| Sessão colaborativa      | outra pessoa ou outro workspace precisa continuar a sessão dentro do G4 OS | outro workspace do G4 OS        |

## Compartilhamento público

Compartilhamento público é o fluxo mais simples da área. Ele publica uma sessão online para leitura e mantém o mesmo link quando você decide atualizar a versão publicada.

### O que você consegue fazer

* publicar uma sessão online
* abrir o link publicado no navegador
* copiar o link
* atualizar o compartilhamento sem trocar a URL
* encerrar o compartilhamento e revogar o acesso

### Fluxo recomendado

1. Abra a sessão que deseja compartilhar.
2. Use o menu de compartilhamento no cabeçalho.
3. Publique, copie ou abra o link.
4. Quando necessário, atualize ou revogue o compartilhamento.

### Casos comuns

* demo assíncrona
* revisão de conversa por outra pessoa
* repasse de contexto para suporte ou operação

## Quando não usar compartilhamento público

* quando a outra ponta precisa continuar a conversa dentro do G4 OS

# Mensagens via Telegram
Source: https://docsg4os.g4business.com/support/telegram-messaging

Conecte um bot do Telegram ao G4 OS para controlar sessões e continuar conversas pelo celular.

## O que é

A integração com o Telegram permite conectar um bot ao seu workspace do G4 OS. Depois de configurado, você pode **parear chats do Telegram com sessões específicas** — e continuar conversando com o assistente diretamente pelo app do Telegram, sem precisar abrir o G4 OS no desktop.

É útil quando você está no celular, em reunião, ou quer receber e enviar mensagens de uma sessão em andamento de qualquer lugar.

## Pré-requisitos

Você precisa criar um bot no Telegram antes de configurar a integração:

1. Abra o Telegram e procure por **@BotFather**
2. Envie `/newbot` e siga as instruções para nomear o bot
3. Ao final, o BotFather entrega o **token do bot** (formato `123456:ABC-DEF...`) — copie e guarde

## Configurar o bot no G4 OS

<Frame>
  <img alt="Configurações do Workspace — seção Telegram com campo de token do bot e lista de chats pareados" />
</Frame>

1. Vá em **Configurações > Workspace**
2. Role até a seção **Telegram**
3. Cole o token do bot no campo **Token do bot**
4. Clique em **Salvar token**

O gateway se conecta automaticamente. O status muda para **online** quando está recebendo mensagens.

> O token fica armazenado no cofre criptografado de credenciais do workspace — nunca em texto claro.

## Parear uma sessão com um chat do Telegram

Com o bot configurado e online, você pode vincular qualquer sessão a um chat:

1. Abra a sessão desejada no G4 OS
2. Clique no menu da sessão (⋯) e selecione **Gateway Telegram**
3. Clique em **Gerar código**
4. Um código de pareamento é exibido junto com o comando `/pair <código>`
5. Abra o Telegram, envie esse comando para o seu bot
6. O bot confirma o pareamento e o chat passa a estar vinculado à sessão

A partir daí, mensagens enviadas naquele chat do Telegram chegam diretamente na sessão pareada — e as respostas do assistente são entregues de volta no Telegram.

## Chats pareados

A seção **Chats pareados** em **Configurações > Workspace > Telegram** lista todos os chats do Telegram vinculados a sessões deste workspace. Para cada chat, você vê qual sessão está ativa no vínculo.

## Desconectar ou remover o bot

| Ação            | O que faz                                                                              |
| --------------- | -------------------------------------------------------------------------------------- |
| **Desconectar** | Para o gateway mas mantém o token salvo; reconecta ao clicar em Salvar token novamente |
| **Remover**     | Apaga o token permanentemente e desvincula todos os chats pareados                     |

## Estados do gateway

| Estado                        | O que significa                                                  |
| ----------------------------- | ---------------------------------------------------------------- |
| **Online**                    | Bot conectado e recebendo mensagens                              |
| **Ativado, mas desconectado** | Token salvo, mas sem conexão ativa — verifique o token ou a rede |
| **Desativado**                | Nenhum bot configurado para este workspace                       |

## Caminho no app

* `Configurações > Workspace` → seção Telegram (configuração do bot)
* `Menu da sessão (⋯) > Gateway Telegram` (parear uma sessão)

## Veja também

* [Controle remoto](/support/remote-control) — acesse a mesma sessão em outro dispositivo pelo navegador
* [Sessão colaborativa](/support/collaborative-session) — compartilhe uma sessão com outro usuário do G4 OS

# Uso
Source: https://docsg4os.g4business.com/support/usage

Acompanhe consumo de créditos e entenda como a política da empresa afeta seus limites no G4 OS.

## O que esta área mostra

A página de `Uso` resume o consumo de créditos do workspace ativo dentro do G4 OS, exibindo limites, projeções e o detalhamento de como os créditos foram gastos no mês.

Em workspaces **vinculados a uma empresa**, a visão passa a refletir a política daquela empresa para o usuário logado: os limites exibidos são os definidos pela administração (política global ou grupo de política específico), e o consumo é calculado dentro desse contexto. Em workspaces **pessoais** sem vínculo empresarial, o comportamento permanece o mesmo.

<img alt="Página de Uso — resumo do mês, ritmo vs. mês passado, projeção, breakdown por modelo e gráfico diário" />

## Estrutura da página

### Badge de escopo

No topo, um badge indica se o consumo exibido é **pessoal** ou vinculado a uma **empresa gerenciada**. Quando vinculado a uma empresa, o nome da organização aparece ao lado do ícone.

### Limites de uso

Dois cartões mostram o consumo atual versus o limite configurado:

| Campo          | Descrição                                                             |
| -------------- | --------------------------------------------------------------------- |
| **Uso diário** | Créditos consumidos no dia corrente. Reseta à meia-noite.             |
| **Uso mensal** | Créditos consumidos no mês corrente. Reseta no início do próximo mês. |

Cada cartão exibe:

* Créditos usados vs. limite (ex: `13,5 de 100 cr`)
* Percentual restante
* Barra de progresso com código de cor:
  * **Normal** (\< 80%): barra escura
  * **Atenção** (80–99%): barra azul
  * **Limite atingido** (≥ 100%): barra vermelha

Quando não há limite configurado, o campo mostra apenas o consumo sem indicador de percentual.

### Resumo do mês

Dois cartões de análise são exibidos lado a lado:

**Ritmo vs. mês passado**
Compara o consumo atual com o mesmo período do mês anterior. Pode mostrar:

* *Acima do ritmo* — consumo percentualmente maior que o mês anterior
* *Abaixo do ritmo* — consumo percentualmente menor
* *No ritmo* — consumo equivalente
* *Sem histórico suficiente* — quando não há dados do mês anterior para comparar

Inclui métricas de créditos, turnos e sessões do mês atual vs. mesmo dia do mês passado.

**Projeção do mês**
Estima o total de créditos que será consumido até o fim do mês com base no ritmo atual. Quando há limite configurado, exibe o percentual projetado em relação ao limite e alerta se a projeção ultrapassar o teto.

### Onde seus créditos foram

Exibe os modelos de IA mais utilizados no mês, com:

* Nome do modelo
* Créditos consumidos e percentual do total
* Número de turnos

Esta seção aparece apenas em contas pessoais ou quando há dados de uso por modelo disponíveis.

### Consumo por dia

Gráfico de barras com o consumo diário de créditos. Permite alternar entre o mês atual e o mês anterior para comparação visual. O totalizador de cada período é exibido acima do gráfico.

> **Nota:** O gráfico considera apenas conexões gerenciadas.

### Como isso se aplica

Seção explicativa sobre o modelo de créditos:

* Créditos são a única unidade exibida no app.
* O uso pessoal continua disponível mesmo fora de um workspace vinculado a uma empresa.
* Quando o workspace está vinculado a uma empresa e o usuário é gerenciado por ela, a tela **Gerenciar Empresa** passa a ser a fonte de verdade das sessões e limites.

## Caminho no app

* `Configurações > Uso`

## Deep links úteis

* [Abrir Uso](g4os://settings/usage)

## Atualizar dados

O botão de atualização (ícone de seta circular) no canto superior direito recarrega os dados de consumo sob demanda.

## Quando os créditos acabam

Se você ou sua empresa atingir o limite mensal configurado, o app bloqueia novas chamadas ao modelo em tempo de execução. A mensagem de erro aparece diretamente na sessão:

> *Limite mensal de créditos atingido.*

**O que acontece:**

* Novas interações com o assistente ficam bloqueadas
* Sessões e histórico permanecem acessíveis para leitura
* O bloqueio é automaticamente removido no primeiro dia do mês seguinte

**Em workspaces gerenciados**, o administrador da empresa pode conceder créditos adicionais ou ajustar o limite sem esperar o reset mensal. Entre em contato com o administrador da sua organização se precisar de acesso imediato.

* [Planos e Créditos](/support/billing-subscriptions) — entenda os planos disponíveis, como resgatar cupons e o que são créditos extras
* [Gerenciar Empresa](/support/empresa) — painel administrativo com visão consolidada do consumo da empresa, tabela de usuários e configuração de políticas

# Workflows

Use workflows para padronizar processos recorrentes e acioná-los por comando dentro das sessões.

## O que são workflows

Workflows são processos reutilizáveis do workspace. Eles descrevem uma sequência de trabalho, contexto de apoio e critérios de execução para que o agente consiga repetir um fluxo com mais consistência.

Diferente de uma skill, que tende a orientar comportamento para uma classe de tarefa, um workflow costuma representar um processo mais completo: diagnóstico, análise, criação de artefato, revisão, handoff ou rotina operacional.

## Onde aparecem

<Frame>

Exemplos:

```text theme={null}
/daily-checkpoint
/slides
/web-app
```

O nome exato depende dos workflows instalados no workspace.

## O que você encontra no detalhe

* nome e slug do workflow
* descrição e comando de acionamento
* instruções do processo
* arquivos de conhecimento associados, quando existirem
* ações para abrir no Finder, enviar para outro workspace ou abrir por deep link

## Casos comuns

* padronizar uma análise recorrente
* criar um processo de revisão ou qualidade

* instalar workflows do marketplace e adaptar para o workspace
* compartilhar um workflow entre workspaces sem copiar instruções manualmente

## Deep links úteis

## Como funciona a sessão

A sessão é conduzida em **quatro fases**, cada uma com um entregável claro.

### Fase 1 — Mapeamento (entrevista guiada)

O G4 OS faz perguntas para entender seu contexto e seus processos atuais:

* Qual é o negócio e seu papel
* Quais categorias do PCF consomem mais tempo ou geram mais dor
* Como funciona o processo mais crítico, passo a passo
* Quais ferramentas e sistemas estão envolvidos
* Onde está o retrabalho, o gargalo e a dependência de pessoa-chave

**Entregável:** lista de processos mapeados com referência ao PCF (Hierarchy ID + nome).

***

### Fase 2 — Documentação (POPs e Playbooks)

Para cada processo mapeado, o G4 OS cria:

**POP (Procedimento Operacional Padrão):**

* Objetivo do processo
* Responsável e participantes
* Gatilho de início e critério de encerramento
* Passo a passo detalhado
* Exceções e como tratar

**Playbook:**

* Contexto e propósito
* Pré-requisitos e recursos necessários
* Fluxo principal com decisões
* Variações e casos especiais
* Checklist de execução

**Entregável:** POPs e Playbooks prontos para usar, exportáveis como Markdown ou documentos.

***

### Fase 3 — Indicadores (Quantidade, Qualidade, Custo)

Para cada processo documentado, o G4 OS propõe indicadores nas três dimensões:

| Dimensão       | O que mede                        | Exemplos                                                      |
| -------------- | --------------------------------- | ------------------------------------------------------------- |
| **Quantidade** | Volume e velocidade de execução   | Nº de processos executados/semana, tempo de ciclo, capacidade |
| **Qualidade**  | Conformidade e acerto na execução | Taxa de retrabalho, % de erros, NPS interno, SLA cumprido     |
| **Custo**      | Recursos consumidos por unidade   | Custo por processo, horas por entrega, custo de retrabalho    |

**Entregável:** dashboard de indicadores com metas sugeridas e método de coleta.

***

### Fase 4 — Otimização

Com processos documentados e indicadores definidos, o G4 OS identifica:

* **Quick wins** (menos de 2 semanas): simplificações, eliminação de etapas desnecessárias, padronização de templates
* **Automações com IA** (1–4 semanas): processos repetitivos que o G4 OS pode executar diretamente
* **Integrações e streamlines** (1–3 meses): conexão entre ferramentas, eliminação de handoffs manuais
* **Redesenho de processo** (3+ meses): reengenharia onde a estrutura atual é o problema

**Entregável:** plano de ação priorizado por impacto × esforço, com responsável e prazo.

# Pentest de App Supabase
Source: https://docsg4os.g4business.com/use-cases/seguranca/seguranca-lovable

Auditoria automatizada de segurança para apps com backend Supabase — RLS, autenticação, isolamento de tenant e exposição de dados.

## O que este caso de uso cobre

O workflow **Segurança Lovable** conduz uma auditoria automatizada de segurança em aplicações web com backend Supabase. Foi criado especialmente para apps gerados no **Lovable** e **Bolt** — mas funciona em qualquer aplicação que use Supabase como backend, independente de como foi desenvolvida.

O workflow verifica RLS, autenticação, isolamento de tenant, escrita anônima e exposição de dados, e classifica os findings com rigor para evitar falsos positivos.

<Warning>
  Esta é uma análise automatizada por IA. Ela cobre os vetores mais comuns mas não substitui um pentest manual profissional. Para aplicações em produção com dados sensíveis, envolva um time de segurança.
</Warning>

## Antes de começar: instalar o workflow

O workflow **Segurança Lovable** precisa estar instalado no seu workspace. Ele está disponível no Marketplace do G4 OS.

<Steps>
  <Step title="Abrir o Marketplace">
    Acesse o Marketplace pelo menu lateral do G4 OS ou pelo deep link abaixo.

    [Abrir Marketplace](g4os://marketplace)
  </Step>

  <Step title="Buscar e instalar">
    Pesquise por **"Segurança Lovable"** e instale no seu workspace. Após a instalação, o workflow fica disponível como `/seguranca-lovable` em qualquer sessão.
  </Step>

  <Step title="Confirmar a instalação">
    Abra uma sessão nova e digite `/seguranca-lovable` — o G4 OS vai reconhecer o workflow e iniciar o fluxo de perguntas.

<Card title="Iniciar auditoria de segurança no G4 OS" icon="shield-halved" href="g4os://action/new-session?input=%2Fseguranca-lovable&send=true&mode=execute&workdir=none">
  Abrir sessão com o workflow Segurança Lovable
</Card>

O G4 OS vai perguntar:

1. **Qual a URL da sua aplicação?**
2. **Que tipo de análise?** — Rápida (Nível 1) ou Completa (Nível 2)

## Níveis de análise

| Nível                  | O que faz                                                        | Tempo     | Créditos |
| ---------------------- | ---------------------------------------------------------------- | --------- | -------- |
| **Nível 1 — Rápida**   | Verifica se dados estão expostos via API pública                 | Minutos   | Baixo    |
| **Nível 2 — Completa** | Tudo do Nível 1 + cria conta real e testa como usuário malicioso | 15–30 min | Médio    |

Se não souber qual escolher: vá de Nível 1. O Nível 2 é recomendado para validar isolamento entre usuários.

## O que o workflow verifica

**Nível 1 — API:**

* Supabase URL e anon key extraídos do JavaScript público
* `service_role` key exposta no frontend (crítico imediato se encontrada)
* Enumeração de tabelas via schema OpenAPI
* Leitura anônima de dados sensíveis por tabela
* Escrita anônima sem autenticação
* Endpoints e mecanismo de login

**Nível 2 — Usuário real (adicional ao Nível 1):**

* Criação de conta real via browser
* Acesso cruzado entre contas (tenant isolation)
* Tentativa de leitura e escrita de dados de outros usuários
* Escalada de privilégios via manipulação de JWT

## Como os findings são classificados

| Ícone | Classificação            | Critério                                                                               |
| ----- | ------------------------ | -------------------------------------------------------------------------------------- |
| 🔴    | **Confirmado**           | Dados sensíveis reais vazaram ou escrita não autorizada funcionou                      |
| 🟡    | **Precisa clarificação** | Pode ser problema ou comportamento esperado — o workflow pergunta antes de classificar |
| ✅     | **Protegido**            | Testado e funcionando como esperado                                                    |

<Note>
  Schema OpenAPI exposto e anon key pública são comportamento padrão do Supabase — não são findings. O workflow não os reporta como vulnerabilidades.
</Note>
